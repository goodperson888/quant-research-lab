# 批量策略研究闭环

## 1. 目标

本里程碑把“冻结 Baseline 后如何研究一个明确改进”从聊天式试参变成可审批、可恢复、
可审计的确定性流水线：

`Baseline → 最多 3 个方向 → Proposal 审批 → Candidate snapshot → ExperimentPlan → Batch Trials → 稳定区间/失败原因 → ComponentEvidence → Candidate/Rejected 摘要`

核心产品指标是：**从用户输入策略，到系统给出第一份有证据的 Candidate 或 Rejected
结论所需的时间**。该指标只衡量流程效率和证据完整度，不是盈利承诺。

## 2. Proposal 与方向

AI Provider 尚未接入，因此系统不生成假建议。人工或 External Agent 可通过同一 API 创建
结构化方向。一个 Baseline 同时最多展示三个活跃方向，每个方向必须包含：

- 精确 Baseline ID 与 subject ID；
- 一个可证伪假设；
- 规则/代码 diff；
- 证据引用；
- ParameterSpace、时间切分和成本模型；
- Objective、风险 Constraint；
- 预计 Trials、时间、失败条件、停止条件和回滚方案。

可复制 `configs/research/improvement-direction.example.yaml`，再运行：

```bash
PYTHONPATH=src .venv/bin/python -m quant_lab.cli \
  create-improvement-direction --config configs/research/YOUR_DIRECTION.yaml
PYTHONPATH=src .venv/bin/python -m quant_lab.cli \
  submit-improvement-direction --proposal-id PROPOSAL_ID
PYTHONPATH=src .venv/bin/python -m quant_lab.cli \
  approve-improvement-direction --proposal-id PROPOSAL_ID \
  --subject-id PROPOSAL_ID --confirmed-by-user
```

状态机为：

`draft → waiting_approval → approved → executing → evaluated → accepted | rejected | expired`

用户批准必须引用 Proposal 自身的精确 `subject_id`。批准后系统创建新的不可变 Candidate
snapshot；Baseline 不被更新或覆盖。预算调整会使等待审批的方向退回 draft，必须重新审阅。

## 3. ExperimentPlan 与搜索策略

第一阶段只支持：

- `grid`：按显式 values 或 lower/upper/step 生成确定性组合；
- `random`：使用固定 seed 生成可复现组合。

不安装或启用 Hyperopt、Optuna。计划预算和 ResearchSession 总预算同时生效；任一不足都
阻止 Job。搜索只向 evaluator 传递 train 与 validation，绝不传递 locked test。最终 locked
test 仍只用于少量冻结候选，并保持串行。

推荐 guided 预算：最多 3 个方向、每方向 20 Trials、总计 60 Trials、45 分钟、locked-test
推荐使用 1 次。硬上限仍为每会话 8 个假设、200 Trials、240 分钟和 2 次 locked-test；推荐
值不是绕过硬上限的权限。

## 4. Batch Trial Engine

通用 Batch Runner 只负责编排，不声称能执行任意策略。真实计算由 `StrategyEvaluator` /
`TrialExecutor` 端口完成。当前存在：

- 进程级 Trial executor：限制并发、时间和 RSS；
- 并发 1 的安全 fallback；
- 明确标记的 deterministic fixture，用于端到端连线测试，不能形成研究结论；
- 原 entry-confirmation 单 Trial Handler 继续作为兼容路径。

每个 Trial 记录：Plan、Baseline/Candidate、参数、参数签名、数据版本、train/validation
split、成本、seed、状态、指标、错误、耗时、峰值 RSS 和 Artifact key。

已成功或明确失败的 Trial 不被恢复流程覆盖。Job 失败、取消或资源超限时，已完成 Trial 和
错误证据继续保留；显式 retry Job 只恢复尚未完成的组合，并且不重复占用会话预算。

## 5. 并发和资源

Worker 仍是 one-shot，Web/API 不执行计算。默认并发为 1；自动建议为：

| 可用内存 | 建议并发 |
|---:|---:|
| 8 GB | 1 |
| 16 GB | 2 |
| 32 GB | 4 |

自动值不得超过 Worker policy 的硬上限。子进程固定常见 BLAS、NumExpr 和 DuckDB 线程为
1，防止进程并发和库内部并发叠加。超时进程会被终止；RSS 超限在可观测时终止并保存原因。

## 6. Trial 存储与稳定区间

SQLite 保存 Trial 状态、关键指标和 Artifact key。详细 Trial 指标按批次写入 Parquet，避免
一 Trial 多个小文件。Parquet 写入使用临时文件后原子替换；原始研究数据和旧实验不迁移、
不覆盖、不自动删除。

结果摘要优先展示：

- Baseline 与稳定候选对比；
- train 与 validation 指标；
- 满足 Constraints 的稳定参数范围；
- 失败参数范围、成本敏感性、Regime 和停止原因；
- 全部 Trial 的分页/查询入口。

孤立历史最高点不是稳定区间，也不会自动成为 Candidate。

## 7. ComponentEvidence 聚合

Batch 完成后可运行 ComponentEvidenceAggregator。逻辑签名由组件类型、规范化规则、Market
Profile 和 timeframe 计算，**不包含单个参数值**。因此多个参数和多个 Trial 归入同一组件
证据，而不是把 `window=10`、`window=20` 各创建一个因子。

证据记录 lineage、来源 Plan/Trials、市场、周期、stable/failed range、增量指标、OOS
状态、Regime、失败条件和 evidence level。只有满足配置的最小增量、交易数和稳定 Trial
条件，才可进入 `component_candidate`；fixture、无增量、随机或交易不足只保留
`diagnostic_improvement`/失败记录。系统永不自动标记 validated。

## 8. 当前真实边界

已实现的是通用编排、持久化、API、Studio 展示和确定性 fixture。尚未实现：

- 任意新策略的通用真实 evaluator；
- 当前 rejected 策略重跑；
- locked test、full stress、Freqtrade Hyperopt 或真实 IStrategy 对账；
- Embedded AI 自动生成方向；
- dry-run 或 live trade。

下一个真实策略 evaluator 必须通过既有 Native Engine adapter 或新的受测端口接入，不能把
fixture 指标描述为策略收益。

Viability 失败后的 ComponentHypothesis 只是进入本闭环的草案入口。它最多生成 3 个方向，
每个建议 3～5 Trials；用户仍需选择方向并一次批准 Diagnostic Batch 预算。若假设来自已
查看 validation，后续 Trial 只能称 screening/contaminated，不能重新包装为独立 OOS。

Selective Reentry 已有真实单组件 evaluator adapter，但本轮没有对 rejected subject 运行
组件 Trials。当前真实执行只完成 artifact-only attribution、Regime screening 和草案生成。

## 9. 验证分级

- `make check-fast`：目标后端测试、compile/typecheck，适合开发内循环；
- `make check-standard`：完整 pytest、JSON/YAML、Skill quick validation、Web lint/typecheck；
- `make check-release`：standard + Next production build + Doctor + OpenAPI/安全测试 + diff check。

关键提交和推送前使用 release；小范围代码迭代先使用 fast，准备审阅时使用 standard。
