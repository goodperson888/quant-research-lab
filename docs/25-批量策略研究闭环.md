# 批量策略研究闭环

## 1. 目标

本里程碑把“冻结 Baseline 后如何研究一个明确改进”从聊天式试参变成可审批、可恢复、
可审计的确定性流水线：

`Baseline → 最多 3 个方向 → Proposal 审批 → Candidate snapshot → ExperimentPlan → Batch Trials → 稳定区间/失败原因 → ComponentEvidence → Candidate/Rejected 摘要`

核心产品指标是：**从用户输入策略，到系统给出第一份有证据的 Candidate 或 Rejected
结论所需的时间**。该指标只衡量流程效率和证据完整度，不是盈利承诺。

## 2. Proposal 与方向

AI Provider 尚未接入，因此系统不生成假建议。人工或 External Agent 可通过同一 API 创建
结构化方向。一个 Baseline 同时最多展示三个活跃方向，每个方向必须包含：

- 精确 Baseline ID 与 subject ID；
- 一个可证伪假设；
- 规则/代码 diff；
- 证据引用；
- ParameterSpace、时间切分和成本模型；
- Objective、风险 Constraint；
- 预计 Trials、时间、失败条件、停止条件和回滚方案。

可复制 `configs/research/improvement-direction.example.yaml`，再运行：

```bash
PYTHONPATH=src .venv/bin/python -m quant_lab.cli \
  create-improvement-direction --config configs/research/YOUR_DIRECTION.yaml
PYTHONPATH=src .venv/bin/python -m quant_lab.cli \
  submit-improvement-direction --proposal-id PROPOSAL_ID
PYTHONPATH=src .venv/bin/python -m quant_lab.cli \
  approve-improvement-direction --proposal-id PROPOSAL_ID \
  --subject-id PROPOSAL_ID --confirmed-by-user
```

状态机为：

`draft → waiting_approval → approved → executing → evaluated → accepted | rejected | expired`

用户批准必须引用 Proposal 自身的精确 `subject_id`。批准后系统创建新的不可变 Candidate
snapshot；Baseline 不被更新或覆盖。预算调整会使等待审批的方向退回 draft，必须重新审阅。

## 3. ExperimentPlan 与搜索策略

第一阶段只支持：

- `grid`：按显式 values 或 lower/upper/step 生成确定性组合；
- `random`：使用固定 seed 生成可复现组合。

不安装或启用 Hyperopt、Optuna。计划预算和 ResearchSession 总预算同时生效；任一不足都
阻止 Job。搜索只向 evaluator 传递 train 与 validation，绝不传递 locked test。最终 locked
test 仍只用于少量冻结候选，并保持串行。

推荐 guided 预算：最多 3 个方向、每方向 20 Trials、总计 60 Trials、45 分钟、locked-test
推荐使用 1 次。硬上限仍为每会话 8 个假设、200 Trials、240 分钟和 2 次 locked-test；推荐
值不是绕过硬上限的权限。

## 4. Batch Trial Engine

通用 Batch Runner 只负责编排，不声称能执行任意策略。真实计算由 `StrategyEvaluator` /
`TrialExecutor` 端口完成。当前存在：

- 进程级 Trial executor：限制并发、时间和 RSS；
- 并发 1 的安全 fallback；
- 明确标记的 deterministic fixture，用于端到端连线测试，不能形成研究结论；
- 原 entry-confirmation 单 Trial Handler 继续作为兼容路径。

每个 Trial 记录：Plan、Baseline/Candidate、参数、参数签名、数据版本、train/validation
split、成本、seed、状态、指标、错误、耗时、峰值 RSS 和 Artifact key。

已成功或明确失败的 Trial 不被恢复流程覆盖。Job 失败、取消或资源超限时，已完成 Trial 和
错误证据继续保留；显式 retry Job 只恢复尚未完成的组合，并且不重复占用会话预算。

## 5. 并发和资源

Worker 可由 `dev.sh` 以 `--watch` 常驻，但 Web/API 仍不执行计算。默认并发为 1；自动建议为：

| 可用内存 | 建议并发 |
|---:|---:|
| 8 GB | 1 |
| 16 GB | 2 |
| 32 GB | 4 |

自动值不得超过 Worker policy 的硬上限。子进程固定常见 BLAS、NumExpr 和 DuckDB 线程为
1，防止进程并发和库内部并发叠加。超时进程会被终止；RSS 超限在可观测时终止并保存原因。

## 6. Trial 存储与稳定区间

SQLite 保存 Trial 状态、关键指标和 Artifact key。详细 Trial 指标按批次写入 Parquet，避免
一 Trial 多个小文件。Parquet 写入使用临时文件后原子替换；原始研究数据和旧实验不迁移、
不覆盖、不自动删除。

每个成功 Trial 额外保留 validation 区间的确定性降采样资金曲线（默认不超过 500 点）。
同一批次的多条曲线合并写入共享 `trial_equity/*.parquet`，SQLite Trial 只登记项目相对
`equity_artifact_key`。普通 Trial 不长期保留完整逐 Bar equity；Baseline 和最终关键
Candidate 仍可按 Run Bundle 保留完整曲线。API 只允许同一 ExperimentPlan、同一 split 和
一致时间覆盖的曲线叠加，旧批次缺少曲线时明确 unavailable，不从 metrics 推算。

结果摘要优先展示：

- Baseline 与稳定候选对比；
- train 与 validation 指标；
- 满足 Constraints 的稳定参数范围；
- 失败参数范围、成本敏感性、Regime 和停止原因；
- 全部 Trial 的分页/查询入口。

孤立历史最高点不是稳定区间，也不会自动成为 Candidate。

## 7. ComponentEvidence 聚合

Batch 完成后可运行 ComponentEvidenceAggregator。逻辑签名由组件类型、规范化规则、Market
Profile 和 timeframe 计算，**不包含单个参数值**。因此多个参数和多个 Trial 归入同一组件
证据，而不是把 `window=10`、`window=20` 各创建一个因子。

证据记录 lineage、来源 Plan/Trials、市场、周期、stable/failed range、增量指标、OOS
状态、Regime、失败条件和 evidence level。只有满足配置的最小增量、交易数和稳定 Trial
条件，才可进入 `component_candidate`；fixture、无增量、随机或交易不足只保留
`diagnostic_improvement`/失败记录。系统永不自动标记 validated。

## 8. 当前真实边界

已实现的是通用编排、持久化、API、Studio 展示、受控通用 DSL 和独立最终保留测试。
尚未实现：

- 超出通用 DSL 范围的任意策略真实 evaluator；
- 当前 rejected 策略重跑；
- 完整重训练式 Walk-forward、更广泛 full stress、Freqtrade Hyperopt 或真实 IStrategy 对账；
- Embedded AI 自动生成方向；
- dry-run 或 live trade。

下一个真实策略 evaluator 必须通过既有 Native Engine adapter 或新的受测端口接入，不能把
fixture 指标描述为策略收益。

Viability 失败后的 ComponentHypothesis 只是进入本闭环的草案入口。它最多生成 3 个方向，
每个建议 3～5 Trials；用户仍需选择方向并一次批准 Diagnostic Batch 预算。若假设来自已
查看 validation，后续 Trial 只能称 screening/contaminated，不能重新包装为独立 OOS。

Selective Reentry 已有真实单组件 evaluator adapter，但本轮没有对 rejected subject 运行
组件 Trials。当前真实执行只完成 artifact-only attribution、Regime screening 和草案生成。

## 9. 验证分级

- `make check-fast`：目标后端测试、compile/typecheck，适合开发内循环；
- `make check-standard`：完整 pytest、JSON/YAML、Skill quick validation、Web lint/typecheck；
- `make check-release`：standard + Next production build + Doctor + OpenAPI/安全测试 + diff check。

关键提交和推送前使用 release；小范围代码迭代先使用 fast，准备审阅时使用 standard。

## 10. 诊断方向排序与组件归档

失败诊断方向由确定性规则分析器按“证据影响 × 样本支持 × 可改性”排序，并按入场/过滤、
退出/持仓、成本/执行、多空方向等类别去重，最多返回三个不同类别方向。它优先读取已保存
信号漏斗中的 `insufficient_reward`、`stop_distance` 和其他过滤原因，不为诊断重新回测。
这些方向始终标记为 `screening_contaminated`，不是 AI 自由建议，也不是独立样本外证据。

组件候选支持软归档与恢复：从活跃列表隐藏时保留 ComponentEvidence、Trial、失败原因和
append-only audit，绝不物理删除负结果，也绝不自动晋升为 validated。

## 11. 一键 Batch 与稳定推荐

`POST /api/improvement-directions/{proposal_id}/launch-batch` 把已审阅 Proposal 确定性
转换为不可变 Candidate、approved ExperimentPlan 和 queued parameter-search Job。重试
复用已有对象，不覆盖旧记录。通用 DSL 只允许搜索 Baseline 已声明参数。

批次总结返回 `recommendation`：

- 无稳定方案：停止扩大搜索；
- 只有一个通过点：标记孤立点，不称候选；
- 存在稳定区间：综合验证表现、回撤、训练/验证差距和邻近参数支持推荐代表 Trial。

生产 Worker 写入 `reports/experiments/<job>.json` 和中文 Markdown；Trial 指标与压缩曲线
继续批量写共享 Parquet。

## 12. 有界候选验证

推荐 Trial 经用户按精确 Plan 批准后，可运行已批准成本、1.5/2 倍成本、三个顺序滚动
窗口、数字参数 ±10% 扰动和使用已收盘标签的行情拆分。它只形成
`ready_for_locked_test_review`、`needs_revision` 或证据不足结论，不自动查看 locked
test，不自动接受 Proposal、晋升生产或启动实盘。

Studio 通过 `candidate-validation-summary` 读取结构化结果，必须直接展示成本敏感性、
正向滚动窗口数、参数扰动通过率、行情证据、最弱证据和下一步。候选验证 Job 创建保持
幂等；重复点击返回同一 Job，不重复消耗预算或生成平行验证。

## 13. 组件到因子候选的受控沉淀

组件候选不会自动写入独立因子库。只有用户确认精确 ComponentCandidate，且对象满足以下
条件时，才允许登记为 `factor status=candidate`：

- 组件状态为 `component_candidate` 且未归档；
- 具有规范化逻辑签名、Market Profile 和 timeframe；
- 具有真实 Trial lineage，不能来自 fixture、未执行或 unavailable 证据；
- metadata 保存来源组件、证据、策略版本、Plan、Trials、成本、Regime 和证据级别；
- `automatic_validation=false`，不能创建 validated/production。

因子候选支持软归档和恢复。归档只把状态改为 `retired`，不删除组件、Trial、负结果或
append-only audit。

## 14. 独立最终保留测试

只有 `ready_for_locked_test_review` 的通用 DSL 候选才能由用户按精确 ExperimentPlan
单独批准最终保留测试。系统冻结推荐 Trial、Candidate、参数、成本和 30 天保留区间，
创建 `generic_strategy_dsl_locked_test` Job：

- 保留区间不参与参数搜索、候选验证或方向生成；
- 同一 Plan 重复点击返回同一 Job，不重复消耗 locked-test 额度；
- 报告保存净收益、回撤、盈亏效率、单笔期望、交易数、trades、equity 和不可变 manifest；
- 通过只表示可进入人工审阅，不自动标记 validated、dry-run、production 或 live trade；
- 查看后如针对该区间继续修改策略，必须废弃原结论并建立新的保留期。

## 15. 失败诊断到候选复测的连续链路

Studio 将失败后的局部研究组织为：

`ComponentHypothesis → 待审阅 Proposal → Candidate Version → Batch Trials → 证据结论`

`POST /api/component-hypotheses/{hypothesis_id}/materialize-proposal` 只把用户明确选择的
组件假设转换为 Proposal 草稿。它必须追溯同一策略唯一的冻结 Baseline，复用已登记的策略
执行配置或同 Baseline 的可信研究契约，并先确认参数能匹配已审阅 evaluator。无法可靠取得
数据切分、成本或执行器时返回 blocked/conflict，不伪造可执行方案。

该动作不提交 Proposal、不创建 Candidate、不批准预算、不排队 Job。Studio 必须先展开显示：

- 冻结 Baseline 保持不变；
- 单一规则 diff 与参数范围；
- 来源证据及污染边界；
- 训练、验证、最终保留区间；
- 成本、目标、约束、Trial/时间预算；
- 失败、停止和回滚条件。

用户再次明确批准精确 Proposal 后，既有 `launch-batch` 才创建一个不可变 Candidate、一个
ExperimentPlan 和有限 Batch Job。多个参数组合只是同一 Candidate 下的 Trials，不是多个
策略。

版本归类统一为：

- 只改参数值：同一 Candidate Version 下的新 Trial；
- 修改单一规则且核心经济逻辑不变：同一 Strategy 下的新 Candidate Version；
- 改变一个主要经济机制：同一 ResearchSession 内的新 hypothesis 分支；
- 核心交易思想、Market Profile 或执行逻辑完全变化：新 Strategy，通常新 ResearchSession。

Studio 默认用友好名称与 v0/v1 展示这棵关系树，技术 ID 下沉到折叠详情。
