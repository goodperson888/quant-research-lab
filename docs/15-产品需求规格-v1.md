# 产品需求规格 v1

状态：目标需求冻结，功能渐进实施

阶段：Phase 0 产品基础

适用范围：单用户、本地优先、研究与 dry-run；不包含实盘

## 1. 一句话定位

Quant Research Lab 是一个**单用户、本地优先、Agent-first、策略优先的可复现个人量化研究工作台**。首页核心入口是“AI 策略研究工作台”，而不是传统指标仪表盘。

产品保留 Codex、Claude CLI 等外部本地 Agent 作为可见的研究执行者；Web 是控制平面、审计台、审批台和结果展示。Web 与 Agent 通过同一组领域白名单、API/未来 MCP 工具和 append-only 审计事件协作。

## 2. 目标用户与价值

首要用户是愿意验证策略而不是购买“稳赚信号”的个人研究者。他们可能从自然语言、Pine Script、公开资料、书籍或视频获得策略想法，但缺少统一的形式化、版本、成本、回测、样本外验证和失败记录流程。

核心价值：

- 原始策略来源、歧义和每次人工决策可追溯；
- baseline v0 冻结且不可覆盖，避免事后改写历史；
- Agent 的计划、工具调用、diff、实验和报告可观察、可暂停、可审批；
- 回测与参数搜索由确定性 Worker 执行，而不是 AI 在对话中无预算盲调；
- 数据、成本、代码、实验和报告保持可复现；
- 默认没有实盘端点、密钥接口或自动生产晋升。

## 3. 非目标

v1/P0 不承诺盈利，不提供交易信号保证，也不替代用户风险判断。第一阶段不实现：

- 实盘、自动下单、自动加杠杆或生产晋升；
- 多用户、租户、云数据库或远程任务队列；
- 完整 TradingView 替代；
- 网页内嵌 AI 作为唯一交互模式；
- 重型机器学习、每日自动挖因子或无预算暴力搜索；
- Redis、Celery、Kafka、PostgreSQL、ClickHouse；
- 完整 MCP Server、Local Connector、Hosted Sandbox 或云端 LLM 调用；
- 在未配置 Provider 时伪造 AI 回复、歧义或建议。

## 4. Agent-first hybrid 产品模型

### 4.1 两种研究模式

1. **External Agent Mode（Phase 0 优先）**：Codex 或未来 Claude CLI/MCP 调用项目 CLI/API/领域工具。Web 读取同一 ResearchSession、Job、Artifact 和审计事件，用户能看见 Agent 在做什么。无需 API key。
2. **Embedded Provider Mode（未来）**：本地 Worker 调用 `LLMProvider` 适配器，如托管模型、Ollama 或 LM Studio。所有输出仍只能是 draft/proposal，不能静默冻结或覆盖策略。

### 4.2 两个独立维度

Agent Provider 与 Execution Target 必须分离，避免未来增加云模式时推翻核心协议。

Agent Provider：

- `external_local_agent`：当前支持，Codex/Claude CLI/未来 MCP；
- `embedded_cloud_provider`：计划中、Phase 0 不支持；
- `byok_provider`：计划中、Phase 0 不请求或托管用户密钥；
- `local_model_provider`：计划中、Phase 0 不启动 Ollama/LM Studio。

Execution Target：

- `local_runtime`：当前支持，本地数据、SQLite Worker Registry、Freqtrade；
- `hosted_sandbox`：计划中、Phase 0 不实现。

当前固定组合是 `external_local_agent + local_runtime`。Web 必须显示 Provider、Execution Target、连接状态、数据位置和隐私提示。

未来可形成两类体验：

- Advanced/Privacy：Web 或桌面控制台 + Local Connector + 本地 Agent/本地数据；
- 普通用户：纯 Web + 平台托管 AI + Hosted Sandbox。

混合模式中的 Local Connector 必须采用主动出站连接或轮询，不要求用户开放本机入站端口。云端策略数据涉及隐私、租户隔离、数据驻留、密钥托管和计算成本，只能进入后期阶段。

## 5. 核心对象

- `ResearchSession`：一次可审计研究会话；
- `Message`、`Attachment`：原始交流与来源；
- `StrategyDraft`、`Ambiguity`、`Proposal`：尚未获用户确认的 AI/人工草稿；
- `StrategyVersion`：不可变 baseline 或后续候选版本；
- `AgentRun`、`AgentStep`、`ToolCall`：Agent 计划、步骤和脱敏工具调用；
- `Artifact`：策略、diff、manifest、实验、报告或日志引用；
- `ExperimentPlan`：单一假设、搜索空间、目标、约束、切分、成本、预算和停止条件；
- `Trial`：确定性实验引擎执行的一次参数组合；
- `Job`：本地 Worker 的排队和执行状态；
- `Approval`：冻结、接受修改或启动高成本任务的显式人工门禁；
- `Report`：链接数据版本和 Run 的研究证据；
- `AuditEvent`：关键动作的 append-only 事实记录。
- `PipelineProfile`、`GateEvaluation`：配置化研究阶段与 correctness/incremental/viability/robustness/locked/dry-run 独立结论；
- `StrategyOutcome`：区分完整策略的 diagnostic improvement、candidate、validated 或 rejected；
- `ComponentEvidence`、`ComponentCandidate`：从策略研究中保留局部 entry/filter/exit/risk/execution 证据；
- `RegimeValidation`：记录 ex-ante detector、适用/禁用/未知状态和分 regime 指标。

## 6. 核心闭环

1. 用户输入自然语言、Pine Script 或文件来源；
2. 系统保存原始来源和时间，不改写原文；
3. Agent/形式化层只生成结构化 draft、歧义和 Proposal；
4. 用户逐项确认；
5. 系统冻结不可覆盖的 baseline v0；
6. 用户或 Agent 创建有边界的 ExperimentPlan；
7. 用户审批需要成本或改变研究状态的动作；
8. API 只创建白名单 Job；本地 Worker 执行确定性回测；
9. Web 展示步骤、日志、Trial、diff、报告和失败原因；
10. 后续每次只验证一个明确假设，并以新版本对比 baseline。

AI 不得静默覆盖策略，不得把聊天文本当唯一事实来源。

## 7. 页面信息架构

### 7.1 `/studio`

三栏结构：

- 左栏：ResearchSession、策略、Agent Runs、append-only 时间线；
- 中栏：用户与 Agent 对话、原始策略/Pine/文件入口；
- 右栏：结构化策略、歧义、ExperimentPlan、diff、审批、Trial、报告与 Artifact。

必须展示当前 Agent Provider、Execution Target、本地 Agent 连接状态和 Embedded Provider 未配置状态。默认 Agent Run Mode 是 `guided`：读取、分析和创建安全研究任务可以自动；冻结 baseline、接受策略修改和启动参数搜索必须显式审批。

### 7.2 其他 P0 页面

- `/strategies`：来源、draft、baseline、版本和状态；
- `/jobs`：queued/running/succeeded/failed/cancelled 与日志；
- `/reports`：基准和实验报告；
- `/data`：Market Profile、UTC 范围、数据集和质量缺口；
- `/settings`：Provider、Execution Target、连接、数据位置和安全状态。

根路径默认进入 `/studio`。

## 8. 状态机

### 8.1 策略状态

`inbox → formalized → baseline → candidate → validated → dry_run → production`

异常/生命周期分支：`degraded`、`retired`、`rejected`。`production` 不存在于 P0 API，未来也必须显式人工批准。

### 8.2 Draft 与 Proposal

`draft → awaiting_confirmation → baseline_frozen`。已冻结 baseline 不能返回 draft，也不能被 UPDATE；任何修改必须创建 Proposal 和新 StrategyVersion。

### 8.3 Job

`queued → running → succeeded | failed | cancelled`。HTTP 请求只创建 Job，不运行长回测。
本地 one-shot Worker 已注册少量明确 Handler；没有 `--job-id` 不执行，未注册类型
不会被伪装为成功。

### 8.4 AgentRun

`queued → running → waiting_approval | paused → completed | failed | cancelled`。暂停/取消是目标协议，Phase 0 只预留状态和 UI。

### 8.5 ExperimentPlan

`draft → approved | rejected`。进入 approved 前必须同时具备：baseline、单一假设、参数空间、目标函数、风险约束、train/validation/locked-test 切分、成本模型、最大 Trials 或时间预算、停止条件和用户批准。

## 9. 参数优化约束

禁止 AI 在对话中逐个试参直到盈利。正确流程：

1. AI 提出一个可证伪的研究假设；
2. 生成 ExperimentPlan，固定 baseline、范围、目标、风险约束、数据切分、成本、预算和停止条件；
3. 用户批准；
4. 确定性 Experiment Engine/Worker 批量执行 Trials；
5. 每个 Trial 记录参数、数据版本、指标、状态和日志；
6. 训练和验证用于搜索，锁定测试只用于少量候选；
7. AI 分析稳定平台和样本外结果并生成 Proposal；
8. 不自动覆盖 baseline，不自动生产晋升。

Freqtrade Hyperopt/Optuna 是未来可选执行器，Phase 0 不安装或启用。未来 Web 可展示参数表、热力图、平行坐标、稳定区间和候选对比。

### 9.1 Fail-fast 与 viability

Pipeline Profile 必须按 `correctness → fast screen → viability → cheap sensitivity →
regime/Pine → full validation/locked/full stress → dry-run` 排序。Standalone strategy 的
viability 由 profile/market/objective 中的 validation 净收益、PF、expectancy、交易数和回撤
阈值评估。只比 baseline 少亏的完整策略不得进入 strategy candidate。

Cheap cost sensitivity 只是 fast-screen kill test。Full stress 只允许 viability 已通过的
同一 subject，且审批必须带精确 subject ID。Pine 来源早期做 semantic/repainting/MTF/
golden trades，完整诊断在 viability 后；自然语言/Python 的完整 Pine 对账同样后移。

## 10. API/MCP 领域白名单

目标工具契约还包括 `list_pipeline_profiles`、`evaluate_gate`、`create_strategy_outcome`、
`create_component_candidate`、`record_regime_validation`。它们与既有 intake、baseline、experiment、
backtest、proposal、report 工具共用同一白名单，不增加 shell/live/secret 能力。

Phase 0 只实现其中的安全子集和 Protocol 占位。工具不接受任意 Shell、任意绝对路径、密钥或 live trade；前端不直接读取 SQLite/DuckDB，也不执行命令。

## 11. 非功能需求

- **可复现**：Run 必须记录代码、数据、参数、成本、时间、随机种子；
- **可审计**：关键动作写入不可更新、不可删除的 AuditEvent；
- **安全默认**：仅监听 `127.0.0.1`，无实盘/密钥/任意 Shell API；
- **本地优先**：数据库、缓存、虚拟环境和 Node 状态留在项目内；
- **轻量**：SQLite + 本地 Worker，不部署服务集群；
- **市场隔离**：验证状态不得跨 Market Profile 传播；
- **解释性**：AI 输出必须保留输入、歧义、diff、工具和审批链；
- **失败透明**：错误和负结果不删除、不静默补零。
- **执行路由**：Agent 必须按 `configs/agent_policies/document-routing.yaml` 读取必需文档、检查前置条件并停在审批门禁；关键控制不得只依赖提示词。详见 [Agent 与 Skill 执行架构](18-Agent与Skill执行架构.md)。

## 12. Phase 0 验收标准

- 现有 CLI 与至少 5 个历史测试继续通过；
- baseline 第二次冻结返回冲突，原快照不改变；
- ExperimentPlan 缺预算/切分/成本/目标时不能 approved；
- FastAPI `/health`、项目状态、会话、intake、freeze、jobs、data、agent status、audit 正常；
- OpenAPI 无 trade/live/shell/credential 端点；
- Studio 是对话 + 结构化成果 + Agent 时间线三栏，不是假聊天框；
- UI 明确显示 `external_local_agent + local_runtime` 与 Embedded Provider 未配置；
- Next build、lint、typecheck 和后端 pytest 通过；
- `scripts/freqtrade.sh trade` 在查找 Freqtrade 前即拒绝；
- 数据、文档和 Freqtrade runtime 未移动或覆盖；
- 功能分支推送，main 不合并。

## 13. Red-Team：最高优先级 kill assumptions

以下按影响 × 可能错误 × 便宜测试排序。现阶段没有证据证明这些假设成立。

### 1. 严谨研究价值足以驱动持续使用或付费

- **Claim（steelman）**：对有真实策略想法的个人研究者，可追溯 baseline、成本和样本外证据比短期信号更有长期价值。
- **Fails if**：目标用户只愿为即时信号付费，完成一次规范基准后不再回来。
- **Evidence this week**：让 5 名目标用户带真实策略完成一次 intake，并记录是否愿意继续第二个假设。
- **Kill criterion**：5 人中少于 2 人愿意在无盈利承诺下继续第二次研究。
- **Cheapest test**：人工陪跑现有 Studio + CLI，不先建设计费。

### 2. AI 形式化不会产生不可接受的静默错误

- **Claim（steelman）**：原文、歧义、diff 和人工确认能把模型错误暴露在冻结前。
- **Fails if**：用户无法发现入场时间、未来函数、成本或执行语义的关键误译。
- **Evidence this week**：用 10 个含歧义的 Pine/自然语言策略做双人规则核对。
- **Kill criterion**：冻结前仍有超过 10% 的关键交易语义错误未被标出。
- **Cheapest test**：只生成结构化草稿和歧义，不生成回测代码。

### 3. 回测结果能与参考平台解释性对齐

- **Claim（steelman）**：统一时区、成交时点、成本和数据可建立可解释差异表。
- **Fails if**：同一 baseline 与 TradingView/Freqtrade 的交易序列无法逐笔解释。
- **Evidence this week**：首个策略选 20 笔交易，逐笔比对信号时点、价格和费用。
- **Kill criterion**：超过 5% 的交易差异无法归因于已记录的数据/执行规则。
- **Cheapest test**：小窗口事件级对账，不先扩展长期历史。

### 4. 产品显著优于 ChatGPT + Freqtrade 手工组合

- **Claim（steelman）**：共享状态机、不可变版本、审批和审计能消除手工粘贴造成的遗漏。
- **Fails if**：用户认为新增结构只是记录负担，完成时间没有下降、可信度没有提升。
- **Evidence this week**：同一策略分别用手工组合和产品骨架完成 baseline，比较时间与遗漏数。
- **Kill criterion**：产品路径既未减少关键遗漏，也增加超过 30% 完成时间。
- **Cheapest test**：只比较 intake → baseline，不先实现复杂图表。

### 5. 用户无需开发者帮助即可完成首个基准

- **Claim（steelman）**：Studio 三栏、明确状态和人工门禁能指导非开发用户。
- **Fails if**：用户在 Market Profile、歧义确认、成本或 baseline 冻结任一步需要工程师介入。
- **Evidence this week**：1 次无提示可用性测试，记录阻塞点。
- **Kill criterion**：目标用户 30 分钟内不能独立完成原始策略保存和 baseline 冻结。
- **Cheapest test**：本地运行 Phase 0 Studio，观察不指导。

## 14. 当前无法判断

尚无真实首个策略、真实用户可用性数据、参考平台逐笔对账、付费意愿或云端单位经济数据。因此本文冻结的是可测试架构和安全边界，不是产品市场契合结论。

## 15. 商业交付与模型兼容需求

- 商业首版面向客户本地安装包或受管容器，通过浏览器使用 Web Studio；默认不交付 Git
  仓库，研究数据和 Provider Key 留在客户机器；
- 许可证到期必须进入只读、可备份、可导出状态，不得删除或扣留客户数据；
- 早期先做付费试点，不把支付、联网许可证、混淆或自动更新伪装成已实现；
- Native Engine 是默认核心，Freqtrade 是客户自行安装、独立进程连接的可选 external
  engine，商业包不捆绑它；
- Embedded/BYOK 模型必须通过 `capability_gated_modern_models_only`：原生 tools、JSON
  Schema、多轮 tool results、至少 32K context、指令层级和中英文；
- 禁止 chat-only、提示词模拟工具、free-text JSON 修补和静默弱模型降级；
- Provider Key 不得进入浏览器持久存储、Git、项目配置、SQLite 或日志；当前不提供 Key
  录入和真实 Provider 调用。

详细决策见 [本地商业交付与模型兼容策略](23-本地商业交付与模型兼容策略.md)。

## 16. 阶段2研究治理

- Regime 必须显式选择 diagnostic 或 validation；前者不得晋升，后者要求同 subject passed
  viability；
- 每个 ResearchSession 有 hypothesis、总 Trials、计算分钟和 locked-test 使用预算；
- 每个 Worker Job 有 RSS、时间、并发和 Parquet batch 预算，超限失败并保留证据；
- Freqtrade lookahead/recursive 仅通过安全包装器运行，属于 correctness，不是收益证据；
- Studio 显示预算和 Regime mode，OpenAPI 仍无实盘、Shell 或密钥能力。

实现边界见 [阶段2研究门禁与资源预算](24-阶段2研究门禁与资源预算.md)。
