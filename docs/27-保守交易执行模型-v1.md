# 保守交易执行模型 v1

## 1. 目标与边界

`conservative_crypto_perpetual_v1` 为 Native Engine 和未来
`StrategyEvaluator` 提供统一的研究级成交、保证金、强平、资金费率和交易所精度语义。
配置位于：

```text
configs/execution_models/conservative_crypto_perpetual_v1.yaml
```

本模型只用于历史研究。它不提交订单、不读取账户、不启动 dry-run/live，也不证明 50x
杠杆安全。默认杠杆仍为 1；任何大于 1 的研究杠杆必须在不可变实验配置中显式声明。

## 2. 执行顺序

每个 bar 的保守处理顺序为：

```text
已知数据和信号
→ 订单价格与数量精度
→ 最小数量/最小名义金额/保证金检查
→ 市价滑点与手续费
→ funding 结算
→ mark price 强平检查
→ protective stop
→ take profit
→ 时间或结构退出
→ 权益与审计记录
```

同一根 K 线同时满足多个条件时：

```text
liquidation → protective_stop → take_profit
```

跳空越过止损或强平线时，使用更不利的开盘/可观测价格，而不是理想触发价。限价单仅触碰
价格不视为必成交；部分成交在 v1 仅作为确定性保守比例或压力情景，不模拟订单簿队列。

## 3. 线性永续保证金

模型区分订单数量、基础资产数量、名义价值、初始保证金、维持保证金、未实现盈亏、
强平费预留、margin balance 和强平状态。

Binance ETHUSDT 使用基础资产数量，OKX ETH-USDT-SWAP 使用合约数量并乘以
`contract_size_base=0.1 ETH`。tick、step、minimum quantity 和 minimum notional 来自
已保存的公开 metadata 快照。

历史杠杆阶梯目前不可得，因此 v1 的 maintenance-margin tiers 明确标记为
`conservative_research_assumption_not_official_historical_tiers`。这些保守档位只用于
kill test，不能表述为交易所历史官方阶梯或用户账户条件。

## 4. 强平

强平由 mark price 判断。若策略数据只有 last-price OHLC 而没有同周期 mark OHLC：

- 可以做显式 fallback 的 smoke/敏感性检查；
- 必须记录 `mark_price_fallback_used=true`；
- 不得称为权威高杠杆验证。

leverage=1 时模型不生成有限强平价。高杠杆时，维持保证金、强平费和缓冲会使强平价比
简单的 `1 / leverage` 更接近入场价。强平交易单独记录 `exit_reason=liquidation` 和
liquidation cost。

## 5. 费用、滑点和 funding

- 默认 taker：0.05%/side；
- 默认滑点：2 bps/side；
- 压力滑点：5 bps/side；
- entry/exit 分别收费；
- funding 使用结算时点的 mark notional；
- funding 缺失只能采用方向不利的非零代理，并记录 imputed；
- 禁止把 funding 缺口静默补零。

## 6. 订单拒绝

以下情况必须产生明确拒绝原因，而不是悄悄修改策略意图：

- `minimum_quantity`；
- `maximum_quantity`；
- `minimum_notional`；
- `insufficient_margin`；
- leverage 未显式批准或超过研究/venue 上限；
- 缺少必要 mark/funding 数据且当前阶段不允许 fallback。

## 7. API 与 UI

只读接口：

```text
GET /api/execution-models
```

Settings 展示 venue、默认和最大研究杠杆、margin mode、强平价格类型、同 K 线优先级、
funding 缺口策略、精度和历史阶梯缺口。不存在创建订单、live、trade 或 credential 接口。

## 8. 当前未实现

- 账户级、历史时点精确 maintenance-margin tiers；
- cross margin、portfolio margin；
- 真实订单簿队列和成交概率；
- 毫秒级延迟；
- ADL、保险基金和交易所破产价格全过程；
- 交易所故障的真实逐事件重放；
- 对现有 rejected 策略的追溯重跑。

这些缺口进入明确压力测试或后续数据任务，不通过“更精确”的措辞掩盖。
