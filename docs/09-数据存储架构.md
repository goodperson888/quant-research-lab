# 数据存储架构

## 一、原则：个人阶段采用混合架构

本项目不把所有数据都塞进数据库，也不把所有状态都散落成文件。个人研究阶段采用
轻量混合架构，让每种格式承担最适合的职责：

- Parquet 保存大体量、列式、可版本化的数据；
- DuckDB 提供本地 SQL 查询、跨文件聚合、视图和报告计算；
- SQLite 保存小型注册元数据与状态；
- JSON/YAML 保存配置和 manifest；
- Markdown/HTML 保存人类可审阅的研究报告。

当前不部署数据库服务，不要求常驻进程，也不需要容器。

## 二、Parquet：大体量数据权威层

以下数据优先使用 Parquet：

- OHLCV K 线；
- 逐笔成交；
- 资金费率；
- 持仓量；
- 标记价格和指数价格；
- 订单簿快照；
- 清洗后的中间与分析数据；
- 因子值和标签；
- 回测交易明细、信号明细和大规模指标结果。

Parquet 适合列裁剪、压缩、分区和跨文件扫描。CSV/JSON 不作为正式大规模行情存储，
只允许用于人工交换、兼容外部工具或小型结果导出，并应注明其非权威用途。

推荐分区层级：

```text
exchange=<venue>/market=<instrument>/symbol=<symbol>/timeframe=<tf>/year=<YYYY>/month=<MM>/
```

逐笔成交或订单簿快照数据量更大，可以在上述层级后按 `day=<DD>` 分区。分区粒度应
在查询裁剪和文件数量之间取平衡，避免产生大量只有几 KB 的小文件。小批次先写入临时
文件或中间区，校验完成后再原子重命名为最终文件。

## 三、DuckDB：本地查询层

建议本地数据库路径：

```text
data/catalog/quant.duckdb
```

DuckDB 用于：

- 直接扫描一个或多个 Parquet 数据集；
- 跨品种、周期、月份和数据版本聚合；
- 建立可重建的视图；
- 数据质量检查；
- 日报、周报、因子健康和回测分析查询。

Parquet 及其 manifest 是可重建分析数据的权威层，DuckDB 是查询与缓存层。DuckDB
文件损坏或丢失时，应能从版本化 Parquet 和建视图脚本重建，而不是反过来依赖 DuckDB
恢复唯一数据。

DuckDB 文件、WAL 和临时文件不进入 Git。重要视图定义、建库脚本和 schema 应进入
版本控制；本地 DuckDB 文件按备份策略另行备份。

## 四、SQLite：注册元数据

SQLite 适合保存体量小、需要事务和索引的注册信息：

- 因子、策略和组件的唯一 ID、版本与状态；
- 实验运行、manifest 路径、结果路径和摘要；
- 按 market profile 隔离的验证状态；
- 数据集版本、文件路径、校验和和质量摘要；
- 失败、退化、淘汰和人工批准记录。

SQLite 不保存大规模 OHLCV、逐笔、订单簿或因子矩阵。当前因子/实验注册表位于
`factor_library/registry.sqlite3`，由 Git 忽略并需要独立备份或定期导出快照。

## 五、配置、manifest 与报告

- JSON/YAML：研究配置、market profile、策略收录、数据 manifest、实验 manifest；
- Markdown：标准流程、研究结论、人工审阅记录；
- HTML：QuantStats、回测和交互式报告；
- 小型 CSV/JSON：仅作人工交换或外部工具导出。

所有机器执行所依赖的配置应可验证、可版本化，并且不得包含密钥。

## 六、Freqtrade 运行时隔离

Freqtrade 的运行状态保持在 `runtime/freqtrade/user_data/`，包括其行情缓存、回测结果、
日志、数据库和本地配置。该目录不是项目统一数据权威层。

需要长期沉淀或跨框架复用的 Freqtrade 数据，应经过来源、时间、质量和校验和审计后，
转换为项目统一的 Parquet + manifest 格式，写入相应 `data/raw`、`data/interim` 或
`data/processed` 版本目录。转换不得覆盖原始下载文件。

## 七、数据完整性与版本要求

每个数据集至少记录：

- 来源、交易所/经纪商、资产类别和工具类型；
- 下载时间与下载工具版本；
- 品种、周期、UTC 起止范围；
- 行数、缺失、重复和异常统计；
- 文件校验和；
- 数据版本和上游版本；
- 清洗、对齐、复权、换月或其他处理步骤；
- 使用的 market profile 与时间可得性语义。

`data/raw/` 只追加、不可覆盖。所有时间戳必须明确 UTC 语义；场所本地时区和交易时段
作为附加字段记录。写入过程使用临时文件、完整性校验和原子重命名，避免半写文件被
研究任务读取。

## 八、何时才升级数据库服务

只有出现以下明确需求时，才评估 PostgreSQL/TimescaleDB：

- 多进程持续实时写入；
- 多台机器共享并发读写；
- 需要稳定 API 服务和细粒度权限；
- 单机文件与 DuckDB 已经成为可测量瓶颈。

ClickHouse、InfluxDB、Redis 等同样只在明确的数据量、吞吐、延迟或缓存需求出现后
评估。当前阶段不引入这些服务，不为可能永远不会出现的规模预先建设机构级设施。

## 九、备份建议

大数据不进入 Git。Parquet 数据、DuckDB、SQLite 注册表、实验结果和报告应执行
3-2-1 备份：至少三份副本、两种介质、一份异地。个人阶段若暂时无法完整实现，最低
要求是“本机工作副本 + 外部磁盘/存储 + 异地或云端加密副本”。

备份必须包含 manifest 和校验和；恢复演练应验证 Parquet 可读、SQLite 一致性以及
DuckDB 查询层可重建。
