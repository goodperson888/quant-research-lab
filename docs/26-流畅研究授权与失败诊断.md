# 流畅研究授权与失败诊断

## 1. 目的

本流程把“每个后台阶段都询问一次”改为“一次批准一个安全、明确、可审计的研究范围”。
用户仍掌握真正改变策略或消耗重要预算的决策，系统可以在授权范围内连续完成机械步骤。

授权不是盈利承诺，也不是执行本身。只有已注册的 `StrategySpec`/`StrategyEvaluator` 和
白名单 Job 才能运行研究；没有执行器时必须显示 blocked/unsupported，不得假装已运行。

## 2. ResearchAuthorization

机器模板位于：

```text
configs/research_authorizations/guided-to-viability.yaml
```

每条授权绑定：

- 精确 `subject_id` 与 `session_id`；
- 允许阶段和 `auto_continue`；
- 最大成本、时间和 Trial 数；
- `locked_test_allowed=false`；
- 停止条件、到期时间和批准人；
- 每个阶段的 append-only 状态、原因和证据引用。

默认 guided 范围可以一次覆盖：

```text
correctness → smoke → fast_screen → viability
```

并可显式附带：

```text
loss_attribution → regime_diagnostic → component_hypothesis_generation
```

授权范围内的内部阶段边界不再重复询问。以下仍是独立人工门禁：

- 解决会改变经济含义的歧义；
- 冻结 Baseline；
- 接受具体 Proposal/Diff 并创建不可变 Candidate；
- 批准组件或参数 Batch 的 Trial/时间预算；
- locked test；
- dry-run；
- live trade（P0 永远不存在）。

## 3. 停止与自动继续

- correctness、smoke 或 fast_screen 失败：立即停止，不进入后续阶段；
- viability 通过：结束本授权或进入另行允许的后续流程；
- viability 失败：完整策略 Outcome 保持 `rejected`；
- viability 失败且授权包含廉价诊断：只继续失败归因、Regime diagnostic 和组件假设生成；
- 预算、依赖、到期或安全边界触发：停止并写 Handoff；
- completed scope 后若还需要 Batch、locked test 或 dry-run：显示真实审批点。

`ResearchAuthorization` 只是审批范围。API 创建授权后，仍需由 External Agent、CLI 或未来
控制平面创建白名单 Job；无注册执行器时不会运行任何阶段。

## 4. Artifact-only Loss Attribution

Viability 失败后优先复用已有 `trades.parquet`、`signals.parquet` 和 `metrics.json`，避免
为了描述性统计重新回测。至少按 train/validation 分开输出：

- long/short；
- exit reason；
- 持仓时长；
- UTC 时段和星期；
- 初始止损距离；
- 费用占毛正收益比例；
- 首次入场/再入；
- 连续胜负；
- 跳过、过滤和取消原因。

报告必须写明：

- `reran_strategy=false`；
- `causal_claim_allowed=false`；
- validation 已经看过，不能再称独立 OOS；
- 未记录的漏斗阶段显示 unavailable，不插值、不猜测。

## 5. 多周期信号漏斗

当前 Selective Reentry 证据展示：

- 1h 趋势腿和方向；
- 15m 回调候选（旧 Artifact 未记录时明确 unavailable）；
- 15m 确认；
- 5m 触发记录；
- 成交数；
- 各过滤、取消和跳过原因。

这表示 5m/15m/1h multi-timeframe 已执行，不表示已完成 multi-period 或 Walk-forward。

## 6. Regime Diagnostic

`regime_diagnostic` 使用已收盘 1h 数据，并延迟到下一根完整 1h bar 生效。输出 detector
version、history days、各状态 trade count/net return/PF/expectancy/drawdown 和
suitable/conditional/blocked/unknown 分组。

它只能是 `screening` 或 `insufficient_history`。已经观察过的 validation 只能形成描述性
关联，不能证明因果，也不能形成正式适用行情声明。正式 `regime_validation` 仍要求同一
subject 已通过 viability。

## 7. ComponentHypothesis 与 Diagnostic Batch

Embedded AI 未实现时，确定性规则分析器最多生成 3 个透明草案。每个草案包含：

- 来源证据；
- 单一 entry/filter/exit/risk/execution 组件；
- 预期改善；
- 小开关或参数空间；
- 3～5 个建议 Trials；
- 失败条件；
- `screening_contaminated` 标记。

草案不会自动运行。用户选择一个或多个方向后，只需批准一次精确的 Diagnostic Batch
预算；Worker 批量执行，不逐 Trial 询问。结果最多进入 `diagnostic_improvement` 或满足
额外证据门槛后的 `component_candidate`，永不自动 validated，也不能恢复已拒绝完整策略。

## 8. Run Bundle 与保留

用户界面把一次运行显示为一个 Run Bundle，而不是多个内部文件：

- manifest、关键 metrics、失败原因：authoritative；
- 必要 trades：为归因保留；
- signals：归因完成后可 archive；
- equity：只长期保留 Baseline、关键 Candidate 或显式 retain；
- 图表和详细日志：rebuildable/archiveable。

旧产物不自动删除。失败 retry 必须引用失败 Job，并保留失败日志和已经完成的阶段证据。

## 9. 当前真实案例

Subject `version_12e1307c9c0e43268f6fdbdda5b9bd20` 的既有 fast_screen 已判定 standalone
viability 失败。本轮只复用已有 Artifact 完成：

- Loss Attribution；
- ex-ante 1h Regime screening；
- 2 个 deterministic ComponentHypothesis 草案；
- Run Bundle `20260727T115825Z-diagnostic-a13da946`。

没有重跑 fast_screen，没有运行组件 Trial、参数搜索、Walk-forward、locked test、正式
Regime validation、dry-run 或 live trade。该策略的 append-only Outcome 仍为 rejected。

## 10. Studio 信息顺序

Studio 的产品顺序固定为：当前结论/下一步、已有 Artifact 的问题归因、最多三个不同类别
方向、已审批批次的进度与停止原因、资金曲线/回撤/多 Trial 指标对比、规则分析器中文总结。
右栏只保留会话上下文、模式、授权进度和预算；subject/job/artifact 等技术 ID 下沉到技术
详情。移动端优先显示结论、下一步、进度和输入，不先堆治理面板。
