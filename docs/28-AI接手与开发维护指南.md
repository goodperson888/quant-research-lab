# AI 接手与开发维护指南

## 1. 用途

本文是新 AI、开发者或新的 Codex 任务接手项目时的最短入口。它不替代领域规范；发生
冲突时，按以下顺序判断：

1. 根目录 `AGENTS.md`；
2. `configs/agent_policies/document-routing.yaml` 为当前 intent 指定的必读文档；
3. `docs/13-当前状态与路线图.md`；
4. 本文；
5. 历史实施计划和旧报告。

运行时研究事实不以 Git 为权威。策略、审批、Job、Trial 和最新 Handoff 以 SQLite、
项目相对 Artifact、checksum 和 append-only audit 为准。Git 只用于用户明确要求的代码
备份或发布。

## 2. 接手后先做什么

1. 完整阅读 `AGENTS.md`，不要只读 README；
2. 阅读 `docs/README.md` 和 `docs/13-当前状态与路线图.md`；
3. 运行 `git status -sb`，保留用户已有修改，不 reset、不覆盖；
4. 运行 `./scripts/dev.sh status`，确认是否已有受托管的 API/Web/Worker/Connector；
5. 按任务 intent 读取路由要求的全部文档；
6. 修改前确认权威状态来自代码、SQLite/Artifact 和测试，而不是某段旧聊天；
7. 完成后执行与风险相称的验证，并明确报告未执行项。

## 3. 当前产品真实边界

截至 2026-08-03：

- Execution Target 固定为本地 `local_runtime`；
- 用户可直接在 External Agent 中研究，也可由网页调用 Local Connector，或在网页配置
  OpenAI-compatible BYOK Provider；
- Local Connector 和 BYOK 当前只负责把模糊策略原文形式化成可审阅草稿，不得自动冻结
  Baseline、扩大研究预算、查看 locked test、晋升生产或实盘；
- 常见 EMA/SMA/RSI/ATR/Bollinger 规则可进入 `generic_strategy_dsl_v1`；
- 价格行为、复杂订单、特殊 Pine 语义和 DSL 外规则需要新增受测 StrategyEvaluator；
- 已实现有界 Batch Trials、稳定区间摘要、同区间资金曲线比较、有界候选验证和单独批准
  的最终保留测试；
- 当前没有 validated、dry-run 或 production 策略，也没有 live trade 能力；
- Freqtrade 是可选外部正确性/对账引擎，不是商业核心依赖，Hyperopt/FreqAI 未启用。
- 离线商业授权位于 `domain/licensing.py`、`infrastructure/offline_licensing.py` 和
  `/api/license/*`；开发模式默认放行，商业构建才启用强制门禁，私钥永不进入仓库。

## 4. 策略与版本语义

不要把每次调整都创建成新策略：

| 变化 | 归类 |
|---|---|
| 只改变一个已批准 Candidate 参数空间内的参数值 | 同一 Candidate 下的新 Trial |
| 修改一条规则，但主要经济机制不变 | 同一 Strategy 下的新 Candidate Version |
| 改变一个主要盈利机制 | 同一 Strategy 下新的 Hypothesis 分支；审阅后形成 Candidate |
| 核心思想、市场对象或执行逻辑改变 | 新 Strategy |

完整关系为：

`Strategy → Baseline v0 → ComponentHypothesis/Proposal → Candidate vN → Trials → Evidence/Outcome`

Baseline 永远不可覆盖。失败策略的局部组件可保留为 diagnostic/component candidate，但
不能因为“少亏”自动成为有效策略或 validated 因子。

## 5. 当前标准用户闭环

1. 用户输入自然语言、Pine 或明确规则；
2. Agent/Connector/Provider 形成结构化草稿并列出歧义；
3. 用户确认后冻结 Baseline v0；
4. 用户按精确 subject 授权到 viability；
5. 确定性 Worker 执行 correctness、smoke、fast screen 和 viability；
6. 失败时复用交易证据做亏损归因、行情 screening 和最多三个改进假设；
7. 用户审阅 Proposal、参数范围、切分、成本、失败条件和 Trial/时间预算；
8. 批准后创建 Candidate、ExperimentPlan 和 Batch Job；
9. Worker 批量执行 Trials，页面展示同区间指标和资金曲线；
10. 稳定方案可单独运行有界候选验证；
11. 通过后才允许一次单独批准的最终保留测试；
12. 系统形成一页结论、最弱证据、适合行情、停止原因和下一步。

机械阶段由程序执行，AI 负责形式化、提出有限假设和解释证据。禁止逐个 Trial 调用 AI、
无限调参或把 locked test 用于搜索。

新增策略不能在核心 Worker 中堆策略名称条件分支；应通过 StrategySpec/StrategyEvaluator
边界接入并添加对应测试。

## 7. 启动与验证

```bash
./scripts/dev.sh
./scripts/dev.sh status
./scripts/dev.sh stop
```

开发修改按风险分级验证：

```bash
make check-fast
make check-standard
make check-release
```

准备提交或推送重要版本时使用 `make check-release`。它应覆盖完整 pytest、配置/Skill
检查、Web lint/typecheck/production build、Doctor、OpenAPI 安全检查和 diff check。
`./scripts/freqtrade.sh trade` 返回退出码 3 是预期安全门禁通过，不是故障。

## 8. 提交前检查

- `git diff --check` 无空白错误；
- 没有 `.env`、Key、Cookie、数据库、日志、runtime 状态或大行情数据进入 Git；
- 没有覆盖 Baseline、删除失败证据或修改 raw 数据；
- 文档中的“已实现/未实现”与代码和测试一致；
- 新 API/Job/Artifact 仍使用精确 subject、白名单和项目相对路径；
- 新功能有测试，前端变化至少通过 typecheck、lint 和 production build；
- 最终回复说明当前状态、停止原因、已完成、未执行、用户是否需要操作和下一步。

## 9. 下一位 AI 不应自行假设

- 不因用户批准策略含义而自动获得参数搜索、locked test、dry-run、实盘或 Git 权限；
- 不把 Local Connector/BYOK 的形式化结果当作用户已批准 Baseline；
- 不把 Trial 当作新 Strategy，也不把规则变更混入旧 Candidate；
- 不把不同日期区间的资金曲线叠加成“多策略对比”；
- 不把 Freqtrade fixture、规则分析器或诊断改善描述为盈利证据；
- 不承诺盈利，不自动 production，不自动实盘。
